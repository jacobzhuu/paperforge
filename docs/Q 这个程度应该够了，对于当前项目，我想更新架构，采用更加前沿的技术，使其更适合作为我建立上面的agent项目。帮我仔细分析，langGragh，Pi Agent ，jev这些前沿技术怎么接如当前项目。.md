## 一、先给出选型结论：三者不是同一层的替代品

| 技术          | 适合承担的职责                                          | 在 PaperForge 中的建议定位             | 不应承担的职责                                           |
| ------------- | ------------------------------------------------------- | -------------------------------------- | -------------------------------------------------------- |
| **LangGraph** | 有状态流程、条件分支、暂停恢复、人工介入、子流程组织    | **主流程编排层**                       | 不替代论文数据模型、引用约束和业务数据库                 |
| **Pi Agent**  | 模型—工具循环、交互式任务、上下文管理、文件与代码工作区 | **可选的工作区执行器或局部工具 Agent** | 不与 LangGraph 同时决定整篇论文的流程和完成状态          |
| **Jev**       | 对给定状态进行分类、评分、有限选项选择                  | **低成本决策组件**                     | 不负责开放式研究规划、正文生成，也不直接充当最终事实裁判 |

这是基于它们接口形态的分工建议：LangGraph 提供图状态与持久化；Pi 提供工具执行循环和会话能力；Jev 返回结构化判断而不是生成文本。([Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/overview))

**对当前项目，我的优先级是：LangGraph 和 Jev 优先，Pi 按具体功能需要引入，而不是为了“技术栈前沿”强行加入。**

## 二、你的项目其实已经具备相当好的 Agent 基础

### 1. 已经不是简单的“调用一次模型写文章”

当前 `worker.py` 的主流程已经包含文献处理、写前证据评估、大纲、正文、质量检查、局部修复、视觉和导出。`_prewrite_evidence_gate()` 会定向补证，`_converge_scholarly_quality()` 会比较修复前后质量，不接受的修改会恢复原稿。

这意味着你已经有：

**执行 → 评估 → 选择是否继续 → 修复 → 再评估**

这样的反馈循环。问题不是完全没有 Agent 能力，而是这些能力主要组织在手写的编排函数中。

### 2. 已经实现了不少不能丢掉的可靠性机制

`JobContext` 管理 checkpoint、事件、停止请求和 LLM 记账；`start_job()` 保存恢复所需的函数与参数，并通过项目行锁避免多个修改产物的任务同时运行。`write_document()` 也已经做到逐节保存，恢复时复用已完成章节。

**架构升级必须保住这些行为，而不是换框架以后重新遇到“任务重复花钱、暂停失效、章节丢失”的问题。**

### 3. 现有科研数据约束，比 Agent 框架更有价值

文稿装配层已经通过 PaperIR 对引用白名单做最终检查；质量检查还关联当前文稿版本、快照哈希、证据定位、人工核验状态，以及原创论文数字的素材溯源。

这些应该成为新 Agent 必须遵守的底层能力：

> **Agent 可以提议如何研究和修改，但不能绕过 PaperIR、证据绑定、版本检查和数字溯源。**

不要把现在这些结构化资产，退化成一个不断增长的聊天记录。

### 4. 当前更明显的不足，是接口仍偏向“流水线调用”

目前 `LLMRequest` 主要是 `system_prompt + user_prompt`，`LLMResponse` 主要返回文本；这套接口没有直接表达多轮消息、工具调用和工具结果。`agenerate()` 使用 `asyncio.to_thread()` 包装同步 provider，已经避免直接阻塞事件循环，但仍不是完整的 Agent 工具运行接口。

因此，不应该把所有新能力都硬塞进现有 `LLMRunner.generate_json()`。更合理的是保留它，再增加独立的工具与决策接口。

## 三、建议的目标架构：一个主编排层，多个受控执行组件

我建议采用下面这套结构：

```text
Next.js 工作台
    │ 目标、审批、进度、证据、修改预览
    ▼
FastAPI
    │ 身份认证、项目权限、任务入口、版本校验
    ▼
ARQ：接收任务、分配执行、唤醒恢复
    ▼
LangGraph：唯一的长期流程编排者
    ├── 研究规划 / 定向补证 / 写作 / 核验 / 局部修订
    ├── LLMRunner：生成、复杂推理、严格语义核验
    ├── DecisionRunner → Jev：低风险分类与路由
    └── Workspace Agent → Pi：可选的文件/代码工作区任务
             │
             ▼
       受限工具与执行环境

业务事实：PostgreSQL + PaperIR + 证据与产物存储
执行位置：LangGraph checkpoint
用户可见过程：统一事件流
```

这里最重要的是**状态归谁管理**。

**PostgreSQL 中的业务表**保存论文、章节、文献、证据、用户修改和正式产物，是业务事实来源。

**LangGraph checkpoint**保存这次运行走到哪里、下一步做什么、等待什么输入，不应另存一份可以与数据库分叉的“正式论文”。

**Pi session**保存某次局部交互的上下文与执行轨迹，不能成为正式文稿的另一个写入源。Pi SDK 本身已经支持持久化会话，因此这里不是“给无状态的 Pi 补状态”，而是明确其状态边界。([Pi](https://pi.dev/docs/latest/sdk))

**Jev**只返回判断结果。是否执行、允许执行什么、何时停止，仍由你的代码决定。

## 四、LangGraph：最值得用于升级现有编排层

### 1. 不要先把整条流程全部重写

我建议第一个迁移对象是：

> **质量修复子流程，而不是整篇论文生成主流程。**

你的现有质量修复已经有明确边界：读取当前报告，找问题章节，保存快照，修复，复查，接受或回滚，最多两轮。这非常适合拆成一个受控子图。

建议结构：

```text
读取指定版本文稿
    → 确定需修复的章节
    → 生成修复提案
    → 必要时等待用户确认
    → 在候选版本上修复
    → 结构检查与语义复查
    → 接受候选 / 丢弃候选
    → 继续一轮 / 结束
```

第一版甚至不需要改变任何模型、提示词和修复规则。**先验证换编排方式后，行为没有退步。**

完成这个子图后，再迁移写前补证，最后接管 `run_full_pipeline()`。

### 2. 原有函数应该变成节点调用的业务能力

| 现有代码                        | 建议迁移方式                                 |
| ------------------------------- | -------------------------------------------- |
| `run_full_pipeline()`           | 逐步变薄，负责选择运行策略并调用图           |
| `_prewrite_evidence_gate()`     | 拆为评估、补证执行、重新评估、结束判断       |
| `_converge_scholarly_quality()` | 拆为候选生成、评估、接受或回滚               |
| `write_document()`              | 初期保持现有写作逻辑，先作为一个业务节点     |
| `JobContext`                    | 保留资源、事件和记账能力，逐步移出图控制职责 |
| `start_job()`                   | 保留任务入口与项目并发控制，增加图运行标识   |

LangGraph 的节点可以调用现有 Python 业务函数，没有必要为了使用 LangGraph，就把所有模型调用和数据访问一起换成另一套封装。([Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/overview))

### 3. 图状态应该小而明确

建议图状态只保存类似这些信息：

```python
# 建议的业务状态结构，不是现有代码
class ResearchRunState(TypedDict):
    project_id: str
    run_id: str
    base_document_version: int | None
    goal: str
    execution_profile: str
    quality_profile: str
    plan_ref: str | None
    artifact_refs: dict[str, str]
    remaining_budget: dict[str, float]
    pending_approval_ref: str | None
    iteration: int
```

不要把整篇论文、全部 PDF 文本、SQLAlchemy session、HTTP client、`JobContext` 实例都塞进 checkpoint。

节点需要材料时，按版本和引用标识从业务层读取。这样更容易控制恢复行为，也更容易确认“这次判断基于哪一版材料”。

### 4. 暂停恢复必须重新设计，而不是套一层 `interrupt()`

LangGraph 支持通过 `interrupt()` 暂停并等待外部输入，恢复时使用同一 `thread_id` 和 `Command(resume=...)`。但恢复会重新执行该节点开头的代码，不是从任意 Python 语句继续。([Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/interrupts))

这对当前项目有两个直接影响：

**第一，不能把 `interrupt()` 包在旧的广泛异常兜底里面。**当前 `_run_stage()` 捕获普通异常并标记降级；LangGraph 官方明确警告，捕获暂停使用的控制异常会破坏暂停行为。审批节点应放在独立的图控制层。 ([Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/interrupts))

**第二，暂停前已经发生的写入必须可以安全重放。**例如“创建文稿版本 → 请求确认”，恢复时不能又创建一个版本。建议审批先生成提案，确认后再经过幂等的业务写入接口提交。

此外，等待用户确认时应释放 worker 执行资源；恢复时重新入队，而不是让一个 ARQ 任务一直占着执行槽。

### 5. ARQ 和 LangGraph 可以共存，但只能有一套流程恢复权威

建议明确：

- ARQ 负责任务投递和执行资源。
- LangGraph 负责图的执行位置、分支和人工介入。
- 业务服务负责幂等、权限、版本和产物一致性。

过渡期可以继续兼容旧的 `checkpoint_json`，但**不要让旧的 `stage_completed()` 和 LangGraph checkpoint 同时独立决定某一步是否需要执行**。

同样需要注意：当前 `LLMRunner` 会把部分失败转成 `None` 或 `JsonResult(error=...)`，而不是抛异常。接入节点重试时，必须把这些结果明确分类，否则图可能把“正常返回的失败结果”当作节点成功。

我建议统一区分：

```
completed / degraded / retryable_failure / needs_input / cancelled
```

而不是继续用“返回了一个字典”隐含成功。

### 6. 不要为了图框架而盲目并行写作

当前 `write_document()` 写完一节后，会注册到 `WritingContext`，给后续章节提供滚动上下文；恢复时也会重新注册已完成章节。

因此，直接把各章节改成并发任务，会改变原来的写作条件。

初期更适合并行的是独立文献处理、独立证据检查。章节并行应放到后续阶段：先固定大纲、术语表、章节论证职责和证据分配，再评估并行带来的速度收益与一致性损失。

## 五、Jev：先建立独立决策层，不要直接替换生成模型

### 1. Jev 应该接在 `DecisionRunner`，不是伪装成普通聊天模型

Jev 的输入是状态与问题，输出包括 `Choice`、`Score`、`Noul` 等结构化判断。官方也已经提供 `langchain-typesafe` 集成，可以作为 Runnable 使用；但部分 middleware 被明确标记为 experimental。([Docs by LangChain](https://docs.langchain.com/oss/python/integrations/providers/typesafe))

建议新增一个你自己的稳定接口：

```text
DecisionRunner
    输入：任务类型、状态、合法选项、策略版本
    输出：判断、概率分布、可用时的 confidence、模型版本、耗时

底层实现：
    JevDecisionProvider
    RuleDecisionProvider
    必要时的 LLMDecisionProvider
```

这样，PaperForge 不需要直接依赖某个实验性 middleware 的内部结构。

生成正文继续使用现有 `LLMRunner`；轻量判断使用 `DecisionRunner`；两者共享成本和运行标识。

### 2. 最适合优先尝试的，是三个有明确边界的任务

**引用软提示。**判断一条 claim 与指定证据是否明显不匹配，用于草稿提示和核验优先级，不直接改变正式 `supported` 状态。

**候选处理优先级。**在已经筛选出的文献或证据中，决定优先处理哪些。初期只改变排序，不永久排除文献，避免误判造成不可见的漏检。

**有限修复动作选择。**例如在已经合法的动作集合中选择“换检索术语”“获取另一份全文”“请求用户补材料”。开放式检索式生成与复杂解释仍交给 LLM。

这里应遵守一个顺序：

> **规则先排除非法动作 → 模型在剩余选项中判断 → 执行前再次校验。**

预算不足、用户锁定的问题、不可修改的实验结果、跨项目访问权限，都不需要 Jev 来决定。

### 3. 当前 citation soft-check 的任务定义，需要一起改

当前 `_quality()` 会将证据摘录按引用键聚合，并截取前 4,000 字符；缺少这些证据时再回退到摘要。`quality.py` 中的软校验提示同时出现“语义相关”和“能否支撑论述”的表述，并定义了 `MAX_SOFT_CHECKS = 40`。

因此，不能只把模型换成 Jev，然后期待校验能力自然提高。

更合理的输入单位是：

```text
一个明确 claim
＋该 claim 绑定的精确 evidence
＋来源定位
＋必要的上下文
＋语言与证据类型
```

尽量避免把“同一篇论文里若干相关段落”混在一起，让模型判断一条具体主张是否被支持。

尤其要把三个概念分开：

**主题相关 ≠ 部分支持 ≠ 完整支持。**

你之前的 `non-weak = 2/3/4` 包含“部分支持”，所以即使 Jev 准确判断为 non-weak，也**不能据此把 claim 标记为完全 supported**。

### 4. 你之前的 shadow 结果支持“草稿提速”，不支持“全面替换核验”

按照你此前提供的实验报告，而非本轮复测：Jev 请求平均约 **1.3–1.4 秒**，原 verifier 约 **30–36 秒**；但 434 对 citation 的 shadow calibration 并未证明存在满足原 fast-path 替代条件的阈值，而且参考标签不是独立人工 gold。

我的判断仍然是：

> 可以接受草稿阶段的可控质量折衷，但应该降低“核验阻塞程度”，而不是偷偷降低“已验证”的含义。

建议快速模式下使用：

```
未核验 → 已完成快速筛查 → 需要深入核验 / 已完成深入核验
```

不要把“快速筛查没发现问题”展示成“引用已验证”。

另外，Jev 官方目前明确表示主要训练语言为英语，中文等 CJK 输入准确率较低。这与你的中文正文、英文证据场景直接相关，应该单独做跨语言评测。([docs.typesafe.ai](https://docs.typesafe.ai/concepts/state))

### 5. confidence、支持程度、错误概率必须分开

对于现有 0–4 档评分，假设返回各档概率，可把：

P(weak)=P(0)+P(1)P(\text{weak}) = P(0) + P(1)

作为待校准的弱支持风险信号，而不是只看平均分。

但这是**你应用层的聚合策略**，需要验证，不能假设天然校准。`Noul` 返回的是某个判断为真的概率；它的 0.5 也不是“中等支持程度”。([Docs by LangChain](https://docs.langchain.com/oss/python/integrations/providers/typesafe))

下一轮评测应重点关注“不支持的引用被放过多少”“高风险数字与比较句漏掉多少”，而不是只看总体一致率。评测集也应按项目隔离，避免同一个项目的高度相似 claim 同时进入开发集和测试集。

上线后记录实际模型版本、问题定义版本和策略版本。官方明确说明 `jev-latest` 会移动，已经调过阈值的系统应该考虑固定版本。([TypeSafe AI](https://docs.typesafe.ai/models))

### 6. 快速模式真正的收益，是改变等待路径

请求变快，不意味着整篇论文也按同样倍数变快。

当前完整流程会等待 `_quality()`，再决定是否导出。

建议把快速草稿策略设计成：

```text
写作完成
    → 引用 ID、结构、数字溯源等确定性检查
    → 交付明确标注为草稿的预览或导出
    → 快速语义筛查更新提示
    → 深入核验作为独立任务执行
```

这比“先跑 Jev，再把大部分请求串行交回原 verifier”更符合你的提速目标。深入核验结果必须绑定文稿版本；用户修改正文后，旧结果应变为过期，而不是继续显示通过。

## 六、Pi Agent：有价值，但应作为局部能力引入

### 1. Pi 最适合补充哪类能力？

我认为它最适合你未来增加这些交互：

> “读取我上传的实验 CSV，核对表 3 的均值与标准差，提出需要修改的位置。”

> “根据这份审稿意见，只修改 Discussion，保留所有实验数字。”

> “检查 LaTeX 编译失败的原因，在隔离目录中生成修复补丁。”

这些任务需要模型反复读取、调用工具、观察结果和调整方案，而不只是走一次固定流程。

Pi 的 Agent Core 已提供工具调用循环、上下文转换与事件流；Coding Agent SDK 则提供更完整的会话、资源和工作区能力。

### 2. 两种接法，不应混为一谈

**接法 A：使用 Agent Core，只注册 PaperForge 领域工具。**

例如：

```text
read_project_context
search_project_evidence
read_section
propose_section_patch
validate_claim_bindings
request_human_review
```

这种方式可控性更强，不必默认开放 shell 和任意文件编辑。但你需要维护一套 TypeScript 运行组件。

**接法 B：使用 Coding Agent 的 SDK 或 RPC，执行工作区任务。**

Python 后端可以通过 RPC 控制独立 Pi 进程。官方 RPC 使用 stdin/stdout 的 JSONL 命令、响应和事件，适合跨语言集成；Node/Bun 进程内集成则适合 SDK。([Pi](https://pi.dev/docs/latest/rpc))

对你当前以 Python 为主的后端，**少量工作区任务先走受控 RPC，比立即重建一个大型 Node Agent 服务更合理。**

### 3. Pi 不应该直接修改正式论文

建议让 Pi 返回一个提案，而不是写入生产文稿：

```text
ArtifactPatch
    base_document_version
    affected_sections
    proposed_changes
    evidence_refs
    generated_artifact_refs
    validation_results
```

然后由 PaperForge 后端检查版本、权限、引用绑定、数字来源，并按用户选择提交。

这能避免：

**LangGraph 在数据库里管理一版文稿，Pi 在工作目录里改另一版，最后不知道哪版是真的。**

同样，Pi 的任务结束不等于论文达到提交要求；全局完成条件仍归主编排和业务核验层。

### 4. 工具限制不等于安全隔离

Pi 官方明确说明，它不内置限制文件系统、进程、网络和凭据访问的完整权限系统；默认继承启动进程的权限。([GitHub](https://github.com/badlogic/pi-mono))

因此，处理用户材料或执行生成代码时，我建议至少做到：

**每次运行独立工作目录，输入只读挂载，输出单独存放，限制外联，生产密钥不进入工作区，设置资源与执行时间上限。**

不能仅靠一句 system prompt：“不要访问其他文件”。

### 5. Pi 和 Jev 可以配合，但不能形成另一套失控流程

在局部 Agent 内，Jev 可以辅助判断某次工具输出是否需要升级检查、某个候选动作是否值得继续。但最终权限检查、预算限制和停止条件仍应是代码规则。

当前 Agent Core 提供工具调用前后与回合结束的扩展点，这让此类接入有明确位置；但具体 API 应锁定版本后再实现。

**不建议让 Pi 再启动一个控制整篇论文的 Planner，与 LangGraph 相互指挥。**

------

## 七、把它做成可复用 Agent 底座，重点是“契约”，不是再加框架

建议第一阶段只抽出几种稳定契约：

**任务契约**：目标、输入版本、可用工具、预算、审批条件、完成条件。

**工具契约**：参数、返回结构、是否有副作用、权限范围、幂等键、是否支持取消。

**修改契约**：基于哪个版本、改哪些部分、证据来源是什么、如何验证和提交。

目录层面可以考虑以下新增结构，名称只是建议：

```text
packages/
    agent_contracts/       # 任务、工具、决策、修改提案的结构
    decision_runtime/     # Jev、规则、LLM 决策适配

services/worker/paperforge_worker/
    graphs/               # LangGraph 编排
    tools/                # 对现有业务能力的受控封装
    pipelines/            # 保留并逐步拆分现有业务逻辑
```

Pi 工作区执行能力等出现实际需求后，再增加对应服务或进程管理模块。

科研方法指导可以组织成 Skills，例如“比较实验结果”“研究缺口分析”“审稿意见修订”。Pi 的 Skills 支持按需加载指导与配套文件，但它们本质上是指导材料，**不是替代参数校验、权限检查和科学约束的机制**。([Pi](https://pi.dev/docs/latest/skills))

------

## 八、前端要保持你之前确定的两个概念正交

你之前关于“快速草稿不应该放到半自动/全自动旁边当第三种模式”的判断是对的。

而且这次代码确认：除了首页的 `writingMode`，后端已经存在 `draft / scholarly / submission` 的 `quality_profile`。不应该再新增一个含义模糊、与它重复的总开关。

建议区分：

| 配置                                              | 回答的问题                 |
| ------------------------------------------------- | -------------------------- |
| `writing_mode: assisted / auto`                   | 用户介入多少？             |
| `execution_profile: standard / fast`，建议新增    | 按什么速度与成本策略执行？ |
| `quality_profile: draft / scholarly / submission` | 产物需要达到什么核验要求？ |

首页可以继续提供简单的“快速草稿”选择，内部映射为快速执行和草稿交付策略。

**即使用户先快速生成，最终选择 submission 时，仍应完成对应核验，不能继承快速筛查的“未发现问题”直接放行。**

工作台也不需要显示“LangGraph 节点”或“Jev middleware”。用户更需要看到：当前目标、计划执行什么、为什么需要补证、哪些章节会修改、哪些判断尚未核验。

## 九、建议按四个阶段推进，而不是一次性重构

### 阶段 0：对齐代码与运行基线

先确认 GitHub 版本、本地 Jev 分支与实际部署版本之间的差异。

建立固定的综述、原创、中文跨语言、缺证据和暂停恢复案例。记录首次可见章节时间、首次草稿交付时间、总成本、引用问题和恢复行为。

这一步不是增加功能，而是防止重构后无法判断是否真的改善。

### 阶段 1：只迁移一个 LangGraph 子图

迁移质量修复子流程，保持模型、提示词和接受规则不变。

验收重点是：重复恢复不重复提交修改；拒绝候选后原稿完整保留；审批对应正确文稿版本；旧质量报告不会错误绑定新稿。

不要为了做“新旧对照”同时执行两次真实写入和付费调用。优先使用固定输入、回放结果和隔离测试环境。

### 阶段 2：接入 Jev 快速执行策略

通过独立决策接口接入，不扩展成整个流程的万能判官。

先开放引用软提示和核验优先级，明确保留“未深入核验”状态；单独评估跨语言、数字、否定、比较与条件限定句。

验收看端到端交付时间和错误放行率，而不是只看 Jev 单请求延迟。

### 阶段 3：增加真正的交互式研究能力，再决定 Pi 范围

选择一个明确用例，例如：

> “根据用户新上传的实验表，核对结果并提出局部修订。”

先完成只读分析、结构化修改提案、人工确认和版本化提交，再逐步允许受限自动执行。

**只有当工作区工具循环确实带来价值时，再扩大 Pi 的职责。普通补证与写作节点，并不需要全部通过 Pi。**

------

## 最终判断

**PaperForge 当前最值得保留的是结构化科研资产与约束；最值得升级的是编排方式、工具接口、运行策略和局部交互能力。**

我会按这个顺序实施：

> **明确领域工具和版本契约 → LangGraph 迁移质量修复与补证子流程 → Jev 支撑快速草稿 → Pi 补充受控工作区任务。**

这条路线既能让项目更接近可持续工作的研究 Agent，也不会牺牲你已经实现的引用真实性、逐节保存、暂停恢复和质量回滚。

**最不建议的方案，是把现有系统推倒，换成多个 LLM Agent 互相对话，再期待 LangGraph、Pi 和 Jev 自动解决可靠性与科研质量问题。框架负责组织能力，PaperForge 自己仍必须定义什么可以做、什么算有证据、什么才算完成。**
