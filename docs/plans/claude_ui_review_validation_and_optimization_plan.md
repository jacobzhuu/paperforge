# Claude UI 审阅核验与 PaperForge 优化计划

> 核验日期：2026-08-02  
> 核验对象：当前工作区代码、现有前端测试、未登录线上入口  
> 计划性质：基于真实实现的修正版，不是对原审阅的照单全收

## 1. 结论摘要

Claude 的总体产品判断基本合理：PaperForge 已经过了“整体换肤”的阶段，下一轮应优先降低流程和状态的不确定性。它指出的“研究型论文不能只凭文件创建”“项目概览与导出中心被单个失败拖垮”“项目卡片不能回答下一步做什么”等问题，均能在当前代码中复现。

但原审阅不能直接作为实施清单，原因有四个：

1. 部分写作台和文献列表结论基于旧实现，当前代码已经修复。
2. 部分建议只改前端表象，忽略后端前置条件、聚合查询和状态模型。
3. P0、P1 混用：认证页信息量是产品暴露范围决定的 P1，不应挤占数据可靠性修复。
4. 审阅遗漏了更严重的问题：项目壳层仍会被白名单接口拖垮，多个校验模块会把“未加载/加载失败”显示成“没有问题”。

因此建议保留原审阅的产品方向，重排实施顺序：

> 先建立“成功、失败、未知、过期”的可信状态语义，再开放文件起稿和优化首次使用，最后建设项目级投稿就绪度与单章重写。

不建议进行整体换肤、重做全站导航或新建冗长营销首页。

## 2. 核验边界与当前基线

### 2.1 已核验范围

- 当前工作区的 Next.js 前端、FastAPI 接口、数据库模型与相关测试。
- 线上根地址的未登录行为：根地址返回 307 并跳转到 `/login?next=%2F`；登录页文案与当前代码一致。
- 官方密码与无障碍规范，仅用于核验原审阅中的 NIST/WAI 结论。

### 2.2 未核验范围

- 没有线上登录态，未对真实项目数据、接口延迟和登录后页面做像素级验收。
- 当前工作区没有 `.git` 元数据，无法确认它是否等同于 Claude 所称的远端 `main` 最新提交，也无法做历史提交对比。
- 本计划只分析和规划，未改动业务实现。

### 2.3 自动化基线

在 `apps/web` 下使用项目声明的 pnpm 版本完成：


现有测试证明当前功能基线稳定，但没有覆盖本文重点提出的“局部请求失败”“文件独立重试”“未知状态不能显示为通过”等场景。

## 4. 原审阅遗漏的高优先级问题

### 4.1 项目壳层仍有辅助接口拖垮整页的问题

[ProjectContext](../../apps/web/components/project/project-context.tsx) 使用同一个 `Promise.all` 获取项目和引用白名单；[ProjectShell](../../apps/web/components/project/project-shell.tsx) 又用统一 `LoadState` 包住全部子页面。白名单失败时，即使项目数据已经成功返回，概览、写作、素材、视觉和导出仍会全部不可用。

这比项目概览内部的六模块聚合更靠前，应列为第一项 P0：项目元数据是硬依赖，白名单是可独立失败的软依赖。

### 4.2 项目进度会把请求失败折算为零

[useProjectProgress](../../apps/web/lib/useProjectProgress.ts) 已使用 `Promise.allSettled`，所以不会整块崩溃；但 rejected 结果会被映射为“0 个任务/0 个文件/无检查问题”，然后正常推断下一步。`allSettled` 只解决了渲染可用性，没有解决状态真实性。

短期必须保留每个维度的 `known/unknown`；长期由项目摘要读模型返回已计算且带新鲜度的状态。

### 4.3 校验面板存在“失败即通过”的假绿色状态

写作页的质量、引用、数字和证据请求彼此独立，但错误状态没有完整传入 [ValidationPanel](../../apps/web/components/writing/validation-panel.tsx)。例如数字检查失败时，研究型论文仍可能显示“本章未发现无法追溯的数值”。

所有质量结论必须满足：

```text
只有请求成功且检查完成，才允许显示“0 个问题”或“检查通过”。
loading / error / stale 一律显示各自状态，并提供重试或修复入口。
```

### 4.4 现有导出分组不是稳定的数据关系

导出记录只有文档版本和时间，没有运行批次外键。当前 5 分钟窗口算法适合展示近似分组，不适合作为“这批投稿文件”的可靠边界。后续若要支持批次重试、审计或整包下载，需要补 `export_run` 实体或至少在产物上记录 `job_id`。

## 5. 修正版实施计划

### 阶段 P0：可靠性、状态语义与文件起稿

#### P0-1 拆分项目壳层的硬依赖和软依赖

涉及文件：

- `apps/web/components/project/project-context.tsx`
- `apps/web/components/project/project-shell.tsx`
- 新增 `apps/web/tests/project-context.test.tsx`

实施要点：

1. 项目元数据单独加载；只有它失败才阻止项目工作区渲染。
2. 白名单暴露独立的 `loading/error/ready/retry` 状态。
3. 白名单失败时，仅禁用依赖它的引用白名单操作并给出重试，其他工作区继续可用。
4. 项目切换时使用请求代次或 AbortSignal，避免旧项目响应覆盖新项目。

退出标准：模拟白名单 500，项目概览、写作和导出仍可进入；页面不把白名单空数组冒充为“已加载且为空”。

#### P0-2 拆分概览、导出和写作校验模块

实施要点：

1. 项目概览的引用审计、任务、成本、版本、导出和数字检查分别使用独立模块状态。
2. 导出中心把“文件列表”作为核心模块，把 PDF 预览、任务/编译诊断、质量门和视觉完整性作为软依赖。
3. 辅助模块刷新或失败时，已经加载成功的导出文件和下载操作始终保留。
4. 写作校验面板接收各检查的显式状态，不再用 `undefined` 或空数组同时表示“没有问题”和“没有数据”。
5. 统一状态枚举：`idle | loading | ready | error | stale`；检查结果另用 `pass | warn | fail`，不要混为一个布尔值。

退出标准：

- 成本接口失败，只在成本卡显示错误和重试。
- 引用审计失败，显示“状态未知”，不得显示“0 个越权引用”。
- 质量报告失败，历史 PDF/Word/LaTeX 等文件仍可查看和下载。
- 数字检查失败，不得显示“未发现无法追溯的数值”。

#### P0-3 支持研究型论文仅凭文件创建

涉及前后端契约：Prompt Canvas、素材上传接口、研究型论文生成前置检查。

实施要点：

1. 提交规则改为：综述必须有研究意图；研究型论文允许“文字或至少一个文件”。
2. 只有文件时，标题取第一个文件的去扩展名，`topic` 保持未填写状态，不写入伪造的研究问题。
3. 文件加入后在创建前显示类型、大小和本地可判定的问题。
4. 上传队列并发上限 3，每个文件独立维护状态和重试；某一文件失败不取消其他成功文件。
5. 不要在失败后直接跳转并丢失 `File` 对象；保留当前队列，允许重试、删除失败项或带已上传结果进入素材中心。
6. 后端暴露统一的文件能力/限制信息，避免前端硬编码 32 MiB 和扩展名后发生漂移。
7. 全自动研究型论文启动前调用材料预检。缺少“含数字的结果数据”或“方法说明/代码”时，项目仍创建成功，但进入素材中心并明确列出缺口；不能只等生成接口返回笼统 409。
8. 辅助模式可直接进入素材中心补充研究问题、主要结果和目标期刊。

退出标准：

- 只上传一个合格素材即可创建研究型项目。
- 只上传普通 PDF 也能保存为项目，但全自动生成前明确提示缺少哪些确定性材料。
- 4 个文件中 1 个失败时，其余 3 个保留成功状态，失败项可以单独重试。
- 刷新/离开前对仍在上传的队列给出明确确认。

#### P0-4 修复项目进度的“未知变零”

短期改造 [useProjectProgress](../../apps/web/lib/useProjectProgress.ts)：

1. 每个来源保留 `known` 和 `error`。
2. 只在所需来源均已知时推断下一步。
3. 任一关键来源未知时显示“部分状态暂不可用”，并链接到对应重试入口。
4. 不在导航层显示未经确认的“已完成/无问题”。

长期由 P1 的项目摘要接口替代前端拼装。

#### P0-5 清理生产环境开发文案

1. `describeError` 按环境返回帮助信息。
2. 生产环境网络错误统一为“服务暂时不可用，请稍后重试或联系管理员”，保留可复制的请求 ID（若后端提供）。
3. 设置页的 `.env` 路径和 `./scripts/dev up` 仅在开发环境显示。
4. 增加生产模式单元测试，防止开发命令再次进入用户文案。

### 阶段 P1：项目管理、无障碍与首次使用

#### P1-1 建设项目摘要读模型，重做卡片信息层级

新增一个由服务端批量计算的 `ProjectAttentionSummary`，不要由前端对每张卡发多个请求。建议字段：

```ts
type ProjectAttentionSummary = {
  projectId: string;
  manuscript: {
    sectionCount: number;
    wordCount: number | null;
    updatedAt: string | null;
  };
  activeJob: {
    stage: string;
    completed: number | null;
    total: number | null;
  } | null;
  readiness: {
    state: "pass" | "warn" | "fail" | "unknown" | "stale";
    attentionCount: number | null;
    nextAction: string;
    href: string;
    checkedAt: string | null;
  };
  latestPdf: {
    createdAt: string;
    stale: boolean;
  } | null;
};
```

数据访问层用聚合查询或固定数量的批量查询，消除现有逐项目计数的 N+1。卡片主信息改为：标题、论文类型与正文规模、下一步、运行状态或最新 PDF；语言和写作模式移到次级信息。

退出标准：项目数量增加时请求数量保持常数级；每张卡最多突出一个下一步；状态未知时不猜测下一步。

#### P1-2 修复选择控件键盘模型

1. 两项论文类型优先改为原生 `select`，或实现完整的共享 Listbox。
2. 项目切换器支持 ArrowUp/ArrowDown、Home/End、Enter/Space、Escape、焦点回到触发器和正确的 `aria-activedescendant`/roving focus。
3. 保留当前文献列表的 `list/listitem + checkbox + button + switch` 结构，不按旧审阅返工。
4. 使用 Testing Library `userEvent.keyboard` 覆盖所有键盘路径。

#### P1-3 修复预览新鲜度和写作页低风险交互

1. 当前章节脏时，预览标签和预览正文顶部显示“基于上次保存版本”。
2. 提供“保存并刷新预览”，保存冲突时停留在编辑视图处理冲突。
3. 将未保存对话框标题改为中性描述。
4. 视觉建议默认显示一行摘要，有待处理项才展开；零建议不长期占用正文上方空间。
5. 全文重写确认文案改为“将生成新的文档版本并切换为当前文稿”；P2 增加恢复旧版本后再评估是否需要更强确认。

#### P1-4 首次使用和认证体验

仅在产品面向新用户开放时启用桌面双栏认证布局；内部部署可只做低成本文案增强。

实施项：

1. 右侧静态说明只回答输入、输出和可信边界；移动端折叠。
2. 共用密码显示/隐藏与 Caps Lock 提示。
3. “显示名称（可选）”明确标注；注册成功显示刚提交的邮箱。
4. 增加通用响应的重发验证邮件接口和服务端限流；绝不返回“该邮箱是否已注册”。
5. 对外发布前完成密码策略决策：15 位单因素密码与有效阻止列表，或 MFA/Passkey 路线。
6. 首页提供 3 条可点击示例和动态提交文案。
7. 导出文案用“文件/投稿文件”，格式说明随勾选项实时变化。

### 阶段 P2：投稿就绪度、导出批次与局部重写

#### P2-1 统一投稿就绪度

用一个后端摘要契约汇总：

- 引用真实性与白名单状态；
- 数字一致性与证据可追溯；
- 撤稿/风险文献；
- 视觉完整性和文稿修改后的过期状态；
- 投稿元数据；
- PDF 编译、版面与导出新鲜度。

每项必须包含 `state`、`checkedAt`、`reason` 和 `fixHref`。项目头部只显示总体摘要；详细修复仍跳回写作、文献、视觉或导出工作台。`unknown` 不参与“通过”计算，`stale` 不能沿用旧的通过结果。

#### P2-2 建立真实导出批次

1. 增加 `export_run`，或至少在每个产物记录 `job_id/export_run_id`。
2. 文件列表按真实批次分组，支持整批下载、批次级失败和重试。
3. 数据迁移后对旧产物保留“历史导出（批次未知）”，不再用时间窗口伪造精确关系。

#### P2-3 设计并实现单章重写

先写 API/交互设计，再实现按钮。最小契约应包含：

- `section_key`、用户重写要求、当前内容和 `expected_updated_at`；
- 允许使用的证据/引用范围；
- 生成结果的引用和数字校验；
- 原文与候选结果的 diff；
- 用户接受后才写入，并创建可恢复版本；
- 冲突、模型失败和质量不通过时保留原文。

单章重写完成前不放置永久禁用入口。

## 6. 验收与测试矩阵

| 场景 | 自动化验收 |
| --- | --- |
| 白名单请求失败 | `ProjectContext` 测试证明项目子页面仍渲染，白名单操作显示未知和重试。 |
| 概览成本失败 | 其他五个成功模块仍显示；成本区域独立错误。 |
| 引用审计失败 | 页面不得出现“0 个问题/检查通过”。 |
| 导出质量失败 | 已生成文件、下载按钮和 PDF 预览（若其自身成功）仍可使用。 |
| 数字检查失败 | 写作校验显示“无法加载”，不能显示“未发现问题”。 |
| 文件起稿 | 无文字、有文件的研究型论文可提交；综述仍必须有研究意图。 |
| 文件部分失败 | 独立失败、独立重试，不重复创建项目，不重复上传成功文件。 |
| 自动生成材料不足 | 项目创建成功，进入素材中心并显示具体缺失条件。 |
| 选择控件键盘 | Tab、方向键、Home/End、Enter/Space、Escape 全路径测试通过。 |
| 预览过期 | 当前章节脏时出现旧预览标记；保存后标记消失并刷新内容。 |
| 项目摘要性能 | 列出 N 个项目时，数据库查询数不随 N 线性增长。 |
| 生产错误文案 | `NODE_ENV=production` 测试中不出现 `.env`、仓库路径或 `./scripts/dev up`。 |
| 移动端 | 390px 下认证、首页、项目卡、写作主要操作、导出不产生横向溢出；触控目标不小于项目既定尺寸。 |
| 投稿就绪度 | 任一检查为 `unknown/stale/error` 时总体不能显示通过，每条警告都有重试或修复链接。 |

每个阶段合入前至少执行：

```bash
cd apps/web
corepack pnpm lint
corepack pnpm test
```

涉及接口和数据库时，再补对应 API/仓储测试；涉及完整创建与导出路径时，增加一条带失败注入的端到端冒烟测试。

## 7. 明确不做的事项

- 不进行全站换色、重新定义字体或增加装饰动画。
- 不新建长篇商业营销首页。
- 不为两个简单下拉强制引入 Radix/shadcn 依赖。
- 不区分“邮箱已注册”，避免账号枚举。
- 不在项目列表通过逐卡请求拼装下一步状态。
- 不把 `undefined`、请求失败或过期报告解释为零问题。
- 不对当前已修复的文献条目语义和全文重写菜单重复返工。
- 不在没有 API、版本和回滚设计时先放一个禁用的“重写本章”按钮。

## 8. 推荐执行顺序

```text
项目壳层失败隔离
  -> 概览 / 导出 / 写作校验的独立状态
  -> 项目进度 known/unknown 语义
  -> 文件起稿 + 上传队列 + 材料预检
  -> 项目摘要读模型与项目卡片
  -> 选择控件、预览与认证体验
  -> 统一投稿就绪度
  -> 真实导出批次和单章重写
```

前四项完成后，PaperForge 才能可靠回答“哪里失败、哪些结果仍可用、当前检查是否真的完成”；在此基础上建设项目卡和投稿就绪度，摘要才不会成为新的误导来源。
