我赞成文献工作台支持 PDF 上传。首页继续作为“项目与素材入口”，文献工作台统一负责 DOI、BibTeX、PDF 和后续证据处理，产品语义会更清楚。

  但 PDF 上传不能只是复用现有 user_asset 接口，而应建立真正的文献链路：

  上传 PDF → 识别元数据 → 匹配/创建文献 → 用户确认 → 私有保存原文 → 全文解析 → 卡片与证据 → 纳入写作

  ### PDF 上传建议

  上传后建议这样处理：

  1. 从 PDF 提取 DOI、题名、作者、年份。
  2. 优先用 DOI 匹配已有 scholarly_work；没有 DOI 时按题名和作者匹配。
  3. 调用 Crossref/OpenAlex 核验元数据，并让用户确认匹配结果。
  4. 已存在文献则把 PDF 绑定到该文献，避免重复条目。
  5. 新文献核验成功后创建文献库条目并分配引用键。
  6. 原始 PDF 私有持久化，解析出章节、页码、表格、证据单元。
  7. 显示状态：待匹配 / 待确认 / 解析中 / 全文可用 / 解析失败。

  需要特别注意：用户上传的 PDF 可能受版权限制，不能像 OA 全文一样存入 shared/oa/... 跨用户共享。应使用用户私有路径，并给 document_file 增加项目或访问范围关联。

  文献工作台入口可以改成一个统一的“添加文献”菜单：

  - 上传 PDF
  - 输入 DOI
  - 粘贴 BibTeX
  - 搜索添加

  ### 当前“勾选”的真实含义

  当前单篇文献左侧勾选会直接将状态切换为 selected，并进入写作白名单，不只是临时 UI 选择，见 apps/web/components/library/library-workbench.tsx:160。后端还会立即持久化 BibTeX key，见
  services/api/paperforge_api/routers/projects.py:619。

  不过顶部“全选”使用的是另一套临时批量选择状态。这两种“勾选”语义有些混淆，建议在界面上明确区分：

  - 单篇开关：纳入写作
  - 批量复选：选择用于批量操作

  ### 入选文献应该如何利用

  最好的原则不是“勾选的每篇都强制引用”，而是：

  > 每篇入选文献都必须被分析和分配，但只有真正支撑句子的文献才进入引用。

  推荐的利用链路如下：

  #### 1. 全文覆盖检查

  文献被纳入后，系统应立即判断：

  - 已有用户上传全文
  - 已获取 OA 全文
  - 只有摘要
  - 无可用文本

  如果缺少全文，应提示用户上传，而不是静默退化为摘要。核心文献只有摘要时，文章质量通常会明显受限。

  #### 2. 逐篇建立“证据画像”

  每篇入选文献都应抽取：

  - 研究问题与贡献
  - 方法、数据集、实验设置
  - 主要结果
  - 局限和适用边界
  - 可定位证据：页码、章节、表格、公式
  - 与其他研究一致、冲突或不可比之处

  当前系统已经在 selected 文献上生成 EvidenceUnit，见 services/worker/paperforge_worker/pipelines/evidence.py:119，方向是对的。

  #### 3. 映射到研究子问题

  不要把所有入选文献塞给所有章节。应把证据映射到具体子问题：

  子问题 A
  ├── 支持证据：论文 1、论文 3
  ├── 反对证据：论文 6
  ├── 条件成立：论文 4
  └── 当前缺口：缺少真实场景验证

  当前系统已经通过证据矩阵和 SYNTH 做了一部分，见 services/worker/paperforge_worker/pipelines/synthesis.py:70。

  #### 4. 用户增加轻量角色标记

  建议允许用户给入选文献标记角色：

  - 核心文献：必须被系统深入分析；若最终未引用，应解释原因
  - 背景文献：适合引言、概念定义、研究历史
  - 方法文献：用于方法分类和技术比较
  - 基准/数据集：用于实验与指标比较
  - 争议/反例：优先用于呈现冲突和边界
  - 一般参考：正常按相关性调度

  不建议只有“必须引用”开关，因为它容易导致无意义的引用堆砌。更好的做法是：核心文献未使用时给出警告，由用户决定是否调整正文。

  #### 5. 写作时传证据，不传整篇 PDF

  Writer 每次只应该获得：

  - 本节需要回答的子问题
  - 相关 EvidenceUnit
  - 对应页码与引用键
  - 支持/反对/条件成立关系
  - 同类研究的可比维度
  - 需要显式报告的证据缺口

  这样比把几十篇全文直接放进上下文更稳定，也更容易控制引用真实性。当前 Writer 已经优先使用 question-aligned evidence，见 services/worker/paperforge_worker/pipelines/writing.py:510。

  #### 6. 生成后给出文献利用报告

  建议文献工作台增加这些状态：

   状态          含义
  ━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   已纳入        用户允许参与写作
  ────────────  ────────────────────────────
   全文可用      有 PDF/XML 并解析成功
  ────────────  ────────────────────────────
   已提取证据    产生了 EvidenceUnit
  ────────────  ────────────────────────────
   已分配章节    至少关联一个子问题或章节
  ────────────  ────────────────────────────
   已进入正文    正文实际产生引用
  ────────────  ────────────────────────────
   未使用        没有足够相关证据，显示原因

  最终应给用户一份类似报告：

  - 入选 35 篇
  - 全文可用 28 篇
  - 产生有效证据 26 篇
  - 分配到章节 23 篇
  - 实际引用 21 篇
  - 4 篇未使用：2 篇主题不符、1 篇仅摘要、1 篇证据重复

  这比简单追求“所有文献都引用”更能提高质量，也方便用户发现检索或大纲的缺口。

  ### 我建议的优先级

  第一阶段先实现：

  1. 文献工作台上传 PDF。
  2. DOI/题名匹配与用户确认。
  3. 私有原文持久化并绑定 scholarly_work。
  4. 复用现有全文解析、卡片和 EvidenceUnit 流程。
  5. 显示全文、证据、章节、正文引用四级状态。
  6. 核心文献未使用告警。

  第二阶段再增加文献角色、证据覆盖率和冲突分析。

  这样用户的“勾选”就不再只是进入引用白名单，而是明确表示：这篇文献必须经过全文分析和证据分配；至于是否最终引用，则由它是否真正支撑正文论断决定。
